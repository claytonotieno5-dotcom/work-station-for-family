# Work Station for Family

Craft & Current is a Node.js/Express website for electrical, tailoring, and developer services. `index.js` exports the Express application using [Vercel's Express integration](https://vercel.com/docs/frameworks/backend/express). `server.js` contains the existing routes and business logic. Vercel serves files from `public/` as CDN static assets; Express static middleware serves them on local and traditional Node.js hosting.

## Requirements

- Node.js 20.6 or newer
- npm
- For Vercel production data: Neon PostgreSQL (pooled connection string)
- For Vercel uploads: a public Vercel Blob store

## Run locally on Windows

Open PowerShell in the project folder:

```powershell
Copy-Item .env.example .env
npm install
npm run dev
```

Open `http://127.0.0.1:3000`. Local development uses `data/site-data.json` and `uploads/` by default, so PostgreSQL and Blob credentials are not required. Change the three role passwords and session secret in `.env` before sharing a development instance. Keep `.env` private; it is ignored by Git.

Run the automated checks with:

```powershell
npm test
```

`npm start` runs the same Express application as `npm run dev`. The app uses `PORT` when supplied and binds to `0.0.0.0` by default in production.

## Data, sessions, and uploads

- In development, site content is read from and written to `DATA_DIR/site-data.json` (default `data/site-data.json`). Writes use a temporary file and rename to reduce corruption risk.
- In production, all profiles, services, projects, comments, and enquiries use the PostgreSQL `application_state` record. Updates are serialized in a database transaction to avoid dropping simultaneous enquiries. The app creates its tables if absent and never resets an existing record.
- On Vercel, use a Neon PostgreSQL pooled connection string in `DATABASE_URL`; the app limits each function instance to one database connection.
- Production login sessions are signed, expire after eight hours, and are checked against the PostgreSQL `app_sessions` table so logout revokes the session across instances. The shared role passwords are provided as environment variables, not stored in site data.
- Project and profile photos are public portfolio images. Local storage is available for development and persistent-volume Node hosts. Vercel must use Blob; the app does not try to write to `/var/task/uploads` or treat `/tmp` as permanent storage.
- Uploaded image names are generated by the server. MIME type, filename extension, size, and image signature are checked. Local file paths never come from the supplied upload name.
- Login attempts are limited to ten per client IP per 15 minutes. Production rate-limit entries and revocable session hashes are stored in PostgreSQL; only a keyed hash of the client address is stored.
- Each provider dashboard has a notification button for new inquiries and unread private messages. Providers can mark incoming messages as read. The badge refreshes every 30 seconds; notifications remain scoped to that provider's own inquiries and conversations.
- The dashboard's Security activity section shows the latest 20 recorded login and access-control events. Failed/rate-limited logins, successful logins, unauthorized dashboard access, rejected notification access, and rejected dashboard request origins are recorded in the existing site data state and capped at 500 events. Logs contain event codes, role, timestamp, and a short keyed source hash; they do not contain raw IP addresses, passwords, customer messages, or contact details. All provider dashboards can inspect this shared, privacy-minimized activity list. These logs support review but do not replace hosting-provider alerts or active intrusion detection.
- Buttons use consistent card-like depth and enlarge slightly on hover or keyboard focus; use normal browser behavior on touch devices.

`data/site-data.json` contains editable profiles and customer enquiries, so it is now ignored and untracked in Git. Keep the existing local file private and backed up for the production import. Earlier commits in repository history may still contain the prior tracked copy; ignoring/untracking it does not rewrite that history.

### Import existing site data

Before the first production request, import the current JSON file into the production database. In PowerShell, set `DATABASE_URL` to the Neon pooled connection string and `BLOB_READ_WRITE_TOKEN` to the Vercel Blob token. The migration script uses Blob automatically when `VERCEL=1`; locally, set `STORAGE_PROVIDER=blob`. `UPLOAD_DIR` is optional and only needed when your local source uploads are in a non-default directory.

```powershell
$env:DATABASE_URL = "<Neon pooled PostgreSQL URL>"
$env:BLOB_READ_WRITE_TOKEN = "<Vercel Blob read/write token>"
$env:STORAGE_PROVIDER = "blob"
npm run migrate:data -- data/site-data.json
```

The importer copies referenced `/uploads/<generated-name>` images to Blob and changes those references before inserting the JSON data. It stops if a referenced image is missing or invalid. It reads from local migration source files only; the deployed application does not rely on those files.

The default import refuses to overwrite an existing `site` record. Back up the database before intentionally replacing it, then explicitly pass `--replace`:

```powershell
npm run migrate:data -- data/site-data.json --replace
```

This replaces the application-state JSON record but does not drop tables or delete upload objects. Keep a verified backup of both the database and upload source files before migrating.

## Environment variables

| Variable | Required | Purpose |
| --- | --- | --- |
| `NODE_ENV` | Host-managed in production | Set to `production` by the host; use `development` locally. |
| `PORT` | No | Assigned HTTP port; defaults to `3000` locally. |
| `HOST` | No | Bind address; defaults to loopback locally and `0.0.0.0` in production. |
| `SESSION_SECRET` | Production | Random secret of at least 32 characters to sign session cookies. |
| `ELECTRICIAN_PASSWORD` | Production | Password for the electrician dashboard. |
| `TAILOR_PASSWORD` | Production | Password for the tailor dashboard. |
| `DEVELOPER_PASSWORD` | Production | Password for the developer dashboard. |
| `DATABASE_URL` | Production | Neon PostgreSQL pooled connection URL used for application data and revocable sessions. |
| `BLOB_READ_WRITE_TOKEN` | When Blob OIDC is unavailable | Static Vercel Blob read/write token for public portfolio images and local data migration. |
| `BLOB_STORE_ID` | Vercel-managed when connected | Blob store ID used with Vercel's managed OIDC authentication. |
| `VERCEL_OIDC_TOKEN` | Vercel-managed when connected | Short-lived Vercel OIDC token; do not set or manage it manually. |
| `STORAGE_PROVIDER` | No | Defaults to `local` outside Vercel and `blob` on Vercel. Set explicitly only to override the provider. |
| `TRUST_PROXY` | Other production Node hosts | Set to `true` behind that host's trusted HTTPS proxy. Vercel proxy trust is enabled automatically. |
| `DATA_DIR` | No | Local JSON data directory; ignored when production uses PostgreSQL. |
| `UPLOAD_DIR` | Optional on non-Vercel hosts | Writable, persistent upload directory when using local uploads on a host volume. Never required on Vercel. |

Generate a production session secret without printing a stored value into source code:

```powershell
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
```

Set secrets through the hosting provider's environment-variable settings, never in `vercel.json`, source files, or a committed `.env`.

## Deploy on Vercel

1. Import the Git repository as a Vercel project and leave framework/runtime detection automatic. Vercel detects the root Express app exported from `index.js`; there is no separate `api/` entry point or catch-all rewrite.
2. Create a **Neon PostgreSQL** project (from Vercel Marketplace or Neon) and copy its pooled connection string to Vercel project **Settings → Environment Variables** as `DATABASE_URL`. Use the pooled/serverless endpoint supplied by Neon.
3. Create and connect a **public Vercel Blob** store because the existing portfolio photos are public. Prefer Vercel-managed OIDC: connecting the store to the project provides `BLOB_STORE_ID` and `VERCEL_OIDC_TOKEN` automatically. If OIDC is not available, set `BLOB_READ_WRITE_TOKEN` as the fallback. Vercel defaults `STORAGE_PROVIDER` to `blob`; do not set it to `local`.
4. Add these other Production environment variables: `SESSION_SECRET` (random, at least 32 characters), `ELECTRICIAN_PASSWORD`, `TAILOR_PASSWORD`, and `DEVELOPER_PASSWORD`. Vercel provides `VERCEL` and `NODE_ENV`; secure proxy handling is automatic. For Blob, provide either managed OIDC credentials (`BLOB_STORE_ID` and `VERCEL_OIDC_TOKEN`) or `BLOB_READ_WRITE_TOKEN`. `UPLOAD_DIR`, `DATA_DIR`, `HOST`, `PORT`, and `TRUST_PROXY` are not Vercel requirements.
5. Before the first public production deployment, import `data/site-data.json` and its referenced legacy uploads into Neon and Blob using the migration steps above. Confirm the local JSON file and image exist first. Back up the database before any use of `--replace`.
6. Keep `public/` at the repository root. Vercel serves files there from its CDN; its Express integration ignores `express.static()`, so no function bundling or catch-all rewrite is needed for these files. This covers the existing CSS, JavaScript, images, and favicon while normal static requests avoid the application function.
7. Deploy, then verify `https://<your-domain>/health` returns `{"status":"ok"}`. Also request `/`, `/electrician.html`, `/tailoring.html`, `/developer.html`, `/favicon.svg`, `/styles/home.css`, `/js/main.js`, and an image under `/images/`. Confirm dashboard login, enquiry persistence, and a small image upload; then redeploy and confirm content remains.

Vercel Functions have a request-body limit (currently 4.5 MB). The upload form and server therefore cap Vercel images at 4 MB (the multipart request cap is slightly larger); conventional Node hosts continue to accept images up to 8 MB. Larger direct-to-Blob uploads need a separate client-upload flow. Check Vercel's current function limits and Blob pricing before launch.

## Deploy on Render, Railway, Fly.io, or another Node host

1. Create a persistent PostgreSQL database and set `DATABASE_URL`.
2. Set `NODE_ENV=production`, all three role passwords, `SESSION_SECRET`, and `TRUST_PROXY=true` in the service environment.
3. Choose either `STORAGE_PROVIDER=blob` plus `BLOB_READ_WRITE_TOKEN`, or `STORAGE_PROVIDER=local` with `UPLOAD_DIR` pointing to a mounted persistent volume. A container filesystem without a persistent volume is not durable upload storage.
4. Set the service start command to `npm start`. The server binds to the assigned `PORT` on `0.0.0.0`.
5. Import data before the app's first request, then verify `/health`, the public pages, login, forms, and uploads.

For Render, attach a persistent disk and check its current plan and region restrictions. For Railway, attach a volume if using local uploads and verify how its service networking exposes PostgreSQL. For Fly.io, use a persistent volume for local uploads and account for its region/replica behavior. Managed database, persistent disk, Blob storage, bandwidth, and backup costs and free-tier limits vary by provider and can change; check current provider pricing and backup/restore procedures. Multiple instances can share PostgreSQL, but local uploads must be on storage shared by every instance or moved to object storage.

## Health checks and troubleshooting

- `/health` returns only application status. In production it checks PostgreSQL connectivity; it returns `503` when the database is unavailable.
- A production startup error names missing configuration variables but never prints their values. Check the service's environment settings and redeploy/restart after changing them.
- A generic `500` should be investigated in the host's function/service logs. Logs contain error categories/codes rather than request bodies or credentials.
- A failed Blob upload returns an error page with `503`; verify `STORAGE_PROVIDER`, the Blob token, and provider status.
- `ENOENT`, permission, or missing-image errors for local uploads mean `UPLOAD_DIR` is missing, not writable, or does not contain migrated files. Do not point it at the deployment source directory unless that host explicitly provides persistent writable storage.
- If a profile still references `/uploads/...` after moving to Blob, run the migration against the original JSON and upload files before replacing application data.
- Never use a temporary filesystem path as the only copy of production content, enquiries, session state, or uploads.

## Known deployment limitations

- Vercel production requires Neon PostgreSQL and Vercel Blob; there is no production JSON or local-upload fallback. Development's JSON mode is for local work only and is not suitable for concurrent or multi-instance production use.
- Portfolio image URLs are public by design. Do not upload private customer documents.
- Vercel uploads are constrained by its function request-body limit as described above. Large images need direct client-to-Blob upload handling.
- Remote deployment, managed database credentials, Blob provisioning, and provider-specific pricing cannot be verified from this repository. Validate each in the provider dashboard before going live.
